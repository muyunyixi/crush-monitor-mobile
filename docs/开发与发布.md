# 开发、接口与发布

## 单一源码归属

本仓库同时包含网页版、小程序和共用 Cloudflare Worker。生产 Worker 只有 `source/worker/index.ts` 一个源码入口，部署配置为 `source/wrangler.toml`，发布工作流为 `.github/workflows/pages.yml`。原小程序仓库保留历史验证版本，但不再作为新版后端的发布来源；不要在第二个仓库创建针对同一个 Worker 的生产部署工作流。

`source/shared/` 是网页及后端的类型和规则；小程序目前使用原生 CommonJS 模块，迁移共享规则时应保持无浏览器 API 的纯逻辑。`source/server/` 提供共用分析实现及网页本地开发服务。它不是独立的第二套生产后端。

## 本地重现

1. 安装 Node.js 22.12 或以上，进入 `source/` 并运行 `npm ci`、`npm test`、`npm run build`。
2. 网页本地开发运行 `npm run dev`；设置 `source/.env` 中的公开 Worker 地址，切勿提交该文件。生成的网页位于 `source/dist/`。
3. 微信开发者工具导入 `source/apps/miniprogram/` 目录。使用自己的小程序 AppID 时同步修改 `project.config.json`，并将 Worker 基础域名加入微信后台 request 和 uploadFile 合法域名。前端服务地址配置在 `services/api.js`；在复刻环境中换成自己的 HTTPS Worker 域名。
4. 创建自己的 Cloudflare 账号、Worker 及微信小程序凭据。`source/wrangler.toml` 中的 Worker 名称、允许网页来源和自定义域名需要与自己的环境一致。先用非生产环境验证，再进行生产发布。

## Worker 环境

| 项目 | 用途 | 位置 |
| --- | --- | --- |
| `TYPESAFE_API_KEY` | 公共模型服务凭据 | Worker Secret |
| `WECHAT_APP_SECRET` | 微信小程序身份验证和 OCR | Worker Secret |
| `WECHAT_APP_ID` | 微信小程序标识 | Worker 普通变量 |
| `MINI_ANALYSIS_DAILY_LIMIT` | 小程序每日分析限额；未设置时分析接口返回 503 | Worker 普通变量；上线前定版 |
| `ALLOWED_ORIGIN` | 网页端浏览器允许的明确来源，逗号分隔 | `wrangler.toml` 或环境变量 |
| `USAGE_LIMITER` | 网页分析、微信 OCR、微信分析和 OCR 临时任务 | Durable Object 绑定与迁移 |
| `CLOUDFLARE_API_TOKEN` | GitHub Actions 生产部署 | 仓库 Secret |
| `PUBLIC_WORKER_URL` | 网页构建时使用的公开 API 地址 | 仓库 Actions Variable |

保留 `keep_vars = true`，确保后续发布不会覆盖控制台配置的普通变量。不要将 Secret 值、原始聊天文本、截图或微信登录凭据写入源码和日志。克隆仓库能取得全部源码；个人凭据、域名所有权及平台权限需要复刻者自行配置。

## 前端兼容约定

| 调用方 | 接口 | 当前行为 |
| --- | --- | --- |
| 网页 | `POST /api/analyze`、`GET /api/quota`、`GET /health` | 按已有分析请求及浏览器 Origin 约束；网页免费额度单独计算 |
| 小程序 v0.4.2 | `POST /api/mini/ocr-async`、`GET /api/mini/ocr-job`、`POST /api/mini/ocr` | 老任务查询协议保留；不要仅因新版本有任务令牌就要求旧客户端提供 |
| 小程序正式版开发分支 | 上述异步 OCR 加 `taskVersion=2`、`X-Ocr-Task-Token`；`POST /api/mini/analyze` | 微信登录验证、任务令牌、消息 ID／revision 校验；生产分析需先确定额度 |

改共享 Worker 时同时运行网页和小程序测试，确认两端接口返回和额度互不干扰。不要将浏览器 Origin 当作小程序身份凭据。任务令牌保护新 OCR 查询，但旧客户端兼容接口仍有历史约束；正式发布前应规划淘汰窗口。分析和识字的重试与扣次应单独核对。

## 发布与回滚

`main` 上与网页或 Worker 有关的路径才触发 `.github/workflows/pages.yml`；工作流先测试、构建，再部署共用 Worker，检查 `/health`，然后更新 GitHub Pages。只改小程序代码时 `.github/workflows/miniprogram.yml` 跑小程序测试，不发布 Worker 或网页。功能开发在分支上不会由上述生产工作流自动部署。

生产发布前记录网页版本、小程序最低兼容版本、Worker 变更、Cloudflare 变量与 DO 绑定。若 Worker 发布后网页或小程序回归失败，停止网页发布并将 Worker 回退到上一通过两端验证的提交；不得从另一仓库覆盖生产 Worker。`/health` 成功只表示基本路由可访问，不能代替 OCR 和模型功能验证。
